# D2 — the four named defect areas, measured

**Measured 2026-07-30 ~21:00 UTC, production, read-only.** Build live `27d6f7b`.

Two of the four were already closed by earlier structural work. The other two
were not defined when the directive was written; they are defined here, from
production, with the numbers that make them checkable next time.

---

## Closed: quick-log double-write

```
duplicate `created` ledger groups, 7 days:  0
```

`ledgerdedup001`'s partial unique index is holding. The master audit measured
7 double-writes per 18 hours; there are none.

**What remains is not this defect.** `api/quick_log.py` still writes directly
with `source="quick_log:ios"` and contains **zero** turn-identity references,
so it creates no canonical turn. That is invariant I1 and belongs to **D4**,
not here. Worth saying explicitly because the index now makes a duplicate
impossible, so a second writer would fail silently rather than duplicate —
and a soft-failed write narrated as success is worse than the duplicate was.
Confirm which before deleting anything.

## Closed: pending-purpose

```
open pendings stacked on (user, kind, item_referenced):  0
```

`pendinguniq001` is holding. `item_referenced` in the key remains load-bearing:
clarification kinds legitimately hold one open row per item.

Currently open: `conversation_hook` 6, `food_clarification` 3, `proactive_hook`
2, `profile_stats` 1, `food_structured_ask` 1. The hook layer still writes its
own rows alongside the structured ones — noise, not duplication, and a
containment question rather than a correctness one.

## OPEN: push reachability — about half of active iOS users cannot be reached

```
active users (7d)                          25
  on iOS with NO device token              12      <-- 48% of all active users
  on telegram with no token                 2      (expected; APNs is not their path)

device_tokens                              49  across 46 users
  revoked                                   2
  last_seen_at older than 14 days          23      <-- 47% of tokens
  never seen                                0
  all rows                                       platform=apns, environment=production
```

**The finding:** the proactive system produced **79 turns in 7 days**, and
roughly half the people it exists to reach have no live token. Twelve active
iOS users have none at all, and 23 of the 49 stored tokens have not been seen
in a fortnight, so the count of genuinely deliverable tokens is nearer 24 than
49.

**Why it has been invisible:** those 79 proactive turns carry **no
`reasoning_json` at all** (see `PHASE6_BASELINE_2026-07-30.md`) and nothing
records a delivery outcome. A push that is never sent and a push that is sent
and dropped look identical from here. So the first fix is not a retry — it is
that a send has an outcome worth recording.

Two users hold multiple tokens (user 26 has 3, user 76 has 2). Whether that is
one device per reinstall or genuine multi-device decides whether they receive
one notification or three; `revoked_at` and `last_seen_at` exist to answer it
and are not being used to prune.

**Split:** token registration is iOS-side (`arnie-ios`); delivery-outcome
recording and stale-token pruning are server-side and can be done here.

## OPEN: HealthKit sync has largely stopped

```
health_snapshots            325 rows, 53 users, 2026-05-09 .. 2026-07-30
  users with a snapshot in the last 7 days      8      <-- of 53 who ever had one
health_import_tombstones     0 rows
wearable_devices             0 rows
```

**The finding:** 53 users have synced health data at some point; **8 have in
the last week.** The table is not stale overall — the most recent row is today
— so this is not a dead pipeline. It is a pipeline that works for a handful of
users and has quietly stopped for the rest, which is the harder failure to
notice and the one nobody was measuring.

`wearable_devices` being **completely empty** is the second half. The Oura
integration merged some time ago; either nobody has ever connected one, or the
connect path does not write the row. Both are worth knowing and only one is a
bug — but with zero rows, no code path that reads that table has ever run in
production, including the token-refresh logic.

`health_import_tombstones` at zero means the import de-duplication/undo
mechanism has also never fired.

**Split:** background delivery and permission re-prompting are iOS-side;
sync-freshness measurement and the empty-`wearable_devices` question are
answerable here.

| Metric | Today | Target |
