### P17g — `decide()` asks whether the SELECTED rung scales authoritatively

`has_mass` was wrong in both directions: `normalize_quantity("2 eggs")` returns
100 g from a **piece-weight table**, so `has_mass` was True for a count no rung
can scale authoritatively. Replaced by `selected_rung_authoritative`, computed
by `select_priced_rung()` — the loop **extracted from `price()`**, consumed by
both routing and pricing so they cannot drift.

`price()` now takes `require_authoritative` **from the caller** (as it already
takes `bound`); `GeneralSettlementOwner._price` passes it. They do not run over
the same rungs — `look()` builds `(memory, None, artifact)`, `assemble()`
supplies `(memory, product, artifact, ESTIMATE)` — so routing could admit on an
authoritative artifact while the pricer fell through to ESTIMATE. Refused
before any write (A8).

### CF20 — a stated size must bind to a record about THAT size

`1 large banana` matched USDA `extra large (9" or longer)` → **152 g** where
the artifact's own `large (8" …)` says **136 g**: +11.8%, reported
`authoritative=True`, citing a record about a different piece. Four defects,
all fixed together:

* `_size_descriptor` compared **one word at a time** against a vocabulary
  holding the two-word `"extra large"` — an entry no input could produce
* the matcher tested token **membership** (`"large"` IS in `{extra, large}`)
* it **fail-opened** on a size it could not represent (`mini`, `tiny`,
  `regular`, `standard`, `double`, `king`, `personal`, `grande`, `tall`,
  `venti` — ten `_SIZE_WORDS` entries with no `_SIZE_TOKENS` counterpart)
* it accepted an **unsized** record for a sized claim — silence read as
  agreement, even with the correct sized record next in the same tuple

Also added `extra small` from the evidence: the artifact states
`extra small (less than 6" long)` = 81 g, which no user could state, so it
priced from the SMALL record at 101 g (+24.7%).

## 5. PROVIDER FRAGILITIES — MEASURED, NOW VISIBLE

### USDA `/foods/search` flakes ~50%, non-deterministically

The **identical** request returns 200 or a **404 HTML error page**: 6/6 failures
unpaced, 4/6 even paced at 1 req/s, with rate-limit budget untouched
(3104 of 3600 remaining). `_search` logged it and returned `[]`.

⛔ **This silently made a provider outage indistinguishable from "USDA has no
such food"** — the dominant bucket of the measurement. Two runs over identical
inputs disagreed wildly (9 recovered vs 2; 132 "no USDA match" vs 99). That
disagreement is the only reason it was caught; a single run would have been
reported as fact.

Fixed: `search_food(..., strict=True)` / `food_portions(..., strict=True)`
raise `UsdaUnavailable` instead of returning `[]`. **Default unchanged — no
production path moves.** The measurement calls strictly behind a bounded retry
(12 attempts, capped backoff, 0.35 s pace). Run 5 absorbed **226** recovered
404s and left 3 unanswered.

### Anthropic qualification resolver — billing

The resolver returned `400 invalid_request_error: credit balance is too low`,
which surfaced as **80 separate `infrastructure UNMEASURED` item rows** — one
account state wearing eighty findings about eighty foods.

Fixed two ways: a **fail-fast preflight** (one USDA search + one qualification
before any item work — 2 calls instead of 152), and **run-level withholding**
(`PUBLISHED=False` with a reason, no item buckets) when the resolver is down at
preflight or dies mid-run. Credit has since been added; preflight now reports
`resolver ok — disposition='qualified'`.

### Outages are never cached

The per-identity cache stored infrastructure outcomes, so one transient 404
became a permanent verdict for that food for the rest of the run — the reason
identical inputs gave 0 unmeasurable items once and 45 the next.
